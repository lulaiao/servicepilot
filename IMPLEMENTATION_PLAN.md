# ServicePilot implementation plan

Each phase is gated. A phase starts only after the previous acceptance criteria
pass. Metrics are `TBD` until generated by a committed configuration and data
manifest.

Every material framework, storage engine, retrieval component, inference model,
and training framework is governed by `docs/adr/0002-selection-governance.md`.
A candidate becomes selected only after a reproducible comparison against the
simplest baseline and credible alternatives.

## Phase 0 — environment and skeleton

Status: **complete**

- Audit host, permissions, GPU/CUDA, Python, Docker, memory, and disk.
- Record core-stack decision and infrastructure blockers.
- Create repository boundaries, configuration placeholders, and a
  dependency-free smoke test.
- Acceptance: `make smoke` passes.

## Phase 1 — deterministic business simulator

Status: **complete**

1. Define enums and typed records for orders, payments, refunds, coupons,
   merchant/delivery state, policy version, and audit events.
2. Define legal order/refund state transitions and deterministic policy
   assertions with evidence IDs and effective times.
3. Add repository protocols plus thread-safe in-memory adapters.
4. Implement synthetic fixtures and deterministic seeded generation.
5. Add write services using idempotency records and optimistic version checks.
6. Test every legal/illegal transition, repeated refund key, stale version,
   amount bounds, cancellation/refund exclusions, and coupon restoration.

Acceptance:

- Core rules pass unit tests without Docker, network, or model dependencies.
- Reusing an idempotency key returns the original result and creates no second
  refund.
- A stale expected version cannot mutate an order.
- Final state and policy applicability are independently assertable.

Evidence: `experiments/reports/phase1_acceptance.md`.

### Phase 4B — Harness Formalization

Status: **complete**. Milestones 1–4 provide the typed runtime/evaluation
boundaries, isolated trials, verify-only zero-write replay, completed-session
resume, tool-step checkpoint recovery, a ten-repetition direct-loop comparison
with identical outcomes, all four required ablations, TOOL-stage Guardrail
enforcement, explicit turn/tool/retry/time/token termination paths, dedicated
confirmation/version-conflict recovery classifications, bounded concurrency,
failure isolation and durable resumable experiment Manifests. ADR 0005 is
Accepted.

Formalize the existing execution and evaluation infrastructure as two typed,
model-independent boundaries:

1. `AgentRuntimeHarness`
   - owns session lifecycle, run configuration and dependency assembly;
   - injects the model/policy, state manager, Router and tool dispatcher;
   - enforces turn, tool, retry, time and token budgets;
   - runs ordered input, tool and output guardrails;
   - records typed events, checkpoints, termination reason and resource usage;
   - supports deterministic replay without issuing business writes.
2. `EvaluationHarness`
   - creates an isolated seeded environment per trial;
   - runs the FSM user simulator and selected runtime harness;
   - applies deterministic state/evidence/forbidden-action grading;
   - supports bounded concurrency, failure isolation and resumable manifests;
   - aggregates metrics without allowing Agent prose to determine success.

Required contracts:

- `HarnessRunConfig`, `HarnessSession`, `HarnessEvent`,
  `HarnessTerminationReason`, `ModelAdapter`, `ToolDispatcher`,
  `GuardrailPipeline`, `CheckpointStore` and `ReplayMode`;
- immutable configuration containing scenario/data hash, code revision, model
  revision, prompt revision, decoding parameters and all budgets;
- append-only trace semantics and payload fingerprints for replay;
- explicit separation between runtime guardrails and the external Judge.

Required comparisons:

- existing direct Agent loop versus the formalized Harness under identical
  scenarios, policy, faults and budgets;
- ablations for tool budget, input guardrail, observation rerouting and
  external Verifier;
- report executable success, false-success, high-risk errors, tool calls,
  turns, latency and Harness overhead.

Acceptance:

- the existing 36 deterministic scenarios retain identical authoritative
  outcomes through the new Harness;
- replay performs zero business writes and reproduces the recorded final
  decision/termination metadata;
- interrupted runs resume from a typed checkpoint without repeating a
  committed high-risk write;
- Prompt Injection, missing confirmation, exhausted budgets and version
  conflicts have explicit termination/recovery paths;
- every reported Harness metric links to code revision, run configuration,
  scenario hash, raw trace and report;
- no external Harness framework is accepted until it beats the lightweight
  internal baseline on a measured requirement.

Progress evidence: `experiments/reports/phase4b_harness_progress.md`.

## Phase 5 — layered memory

Status: **complete**. Added recent-window, typed working memory, deterministic
factual summaries and consented long-term memory with source precedence,
conflict records, expiry, revocation, deletion and privacy tests. The 20-turn
and stale-summary gates pass; the no-memory ablation is evidence-scoped as a
Memory capability metric.

Evidence: `experiments/reports/phase5_acceptance.md`.
Decision: `docs/adr/0006-layered-memory-boundary.md`.

## Phase 6 — hybrid retrieval and evidence verification

Status: **in progress**. Phase 6A froze an initial gold-evidence corpus/query
set, added BM25, metadata filters, ranking metrics and deterministic evidence
sufficiency checks. Dense and reranker models remain `TBD`; the initial set is
too small/easy to justify them.
Freeze the corpus and compare lexical-only, dense-only, hybrid, and reranked
variants under the same latency and retrieval budget before accepting components.

Progress: `experiments/reports/phase6_progress.md`.
Proposed decision: `docs/adr/0007-phase6-retrieval-components.md`.

## Phase 7 — monitors, recovery, and full evaluation

Status: pending. Calibrate bounded deterministic/quality monitors, cover at
least ten fault classes, and scale to at least 1,000 executable trajectories.

## Phase 8 — trajectory data loop

Status: pending. Add redaction, deduplication, leakage-resistant splits,
manifests, hard-negative mining, and reproducible SFT/preference exports.

## Phase 9 — SFT and GRPO

Status: pending and blocked on GPU re-audit. Run small-model LoRA SFT, outcome
GRPO, process-reward experiments, reward-hacking audits, and repeated trials.
Training model/framework choices require a new ADR backed by measured fit,
throughput, peak VRAM, disk, stability, license, and downstream task quality.

## Phase 10 — open-source delivery

Status: pending. Validate a clean-environment quick start, demo, trace viewer,
reports, ablations, and evidence-linked resume statements.
